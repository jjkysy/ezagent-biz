# 开发流程 · 10 分钟定版

## 一、流程总图（真相源接力）

```
 
 定位稿 → 痛点清单 → 认领映射 → 线框/原型 → 功能spec卡 → issue → 测试套件 → PR → 指标读数
 (产品)   (产品)     (产品)     (产品+设计)  (产品+研发)  (研发)  (研发)    (研发) (运营)
   └────────── 每个箭头 = 一次"真相源交接" = 一道 gate（上一件不合格不放行）─────────┘
                                  测试用例=spec卡Gherkin（不另写）│ 只做该功能+测试绿才合PR │ drop:不达标砍子树

贯穿全链：① ROI/北极星（飞书OKR + 看板）  ② 日/周/月节奏  ③ 三位一体（每个开发节点必带"产品+运营"兄弟）
```

## 二、环节明细表（输入 / 产出 / 钦定真相源 / 负责人 / 工具）

> "工具"列：**可直接调 API / 可模仿其形态**；外部工具只贡献能力，真相落 ezagent 库。

| # | 环节 | 输入（真相源） | 产出物 | **钦定下一环节的唯一真相源** | 负责人 | 工具（调用/模仿） |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | **战略/定位** | 团队产品意图 | 价值主张 · PR/FAQ · 交易公式 | **一页定位稿**（价值主张为主，PR/FAQ·交易公式作附件） | 产品负责人 | 飞书 docx；Miro 根节点 |
| 2 | **痛点** | 定位稿 | 多张痛点卡 · 优先级打分 | **排序后的痛点清单**（机会树） | 产品 | 飞书 docx/bitable；Miro / xmind 机会树 |
| 3 | **用户锚定** | 痛点清单 | 团队画像 · 零教育成本评估 · 岗位↔层映射 | **岗位↔认领层映射表**（决定后面谁认领） | 产品负责人 | 飞书 bitable |
| 4 | **体验主张** | 痛点清单 | 四条 UX 承诺 · 线框/原型 | **主界面线框/原型** | 产品 + 设计 | excalidraw；**html：Lovable / Zeplin** |
| 5 | **功能/模块** | 线框/原型 | 模块(价值闭环) · 功能 spec · 用户故事 · 验收 · ICE · 价值卡 · 挂钩牌 ← *产出最多* | **功能 spec 卡**（每功能一张，模板 `06·G-r`：用户故事+Gherkin 验收+ICE+价值卡+挂钩牌） | 产品 + 研发 | 飞书 docx；**Zeplin**；markmap 节点 |
| 6 | **issue** | 功能 spec 卡 | issue（含范围/不做/验收用例） | **issue 本身** | 研发 | GitHub（REST/GraphQL） |
| 7 | **测试** | issue（携带 spec 卡 Gherkin） | 测试代码 · 测试结果（绿/红）　*用例=spec卡Gherkin，不另写* | **可跑且对应 Gherkin 的测试套件**（必须变绿才交 PR） | 研发 | dev-loop：test-plan-generator→test-code-writer→test-runner；`mix test` / CI |
| 8 | **PR** | 测试套件（写实现让它变绿） | PR · 测试通过 · 过 gate | **合并后的 PR** | 研发 | GitHub + reviewer 过 gate 清单 |
| 9 | **验证/运营** | 合并 PR（上线功能） | 运营帖 · 网页 · changelog · 指标 ← *产出多* | **指标读数**（对照 drop 阈值） | 运营 | 指标采集见下「验证指标工具」；changelog 飞书；drop 阈值 |
| 贯穿 | **ROI/北极星** | 各环节真相源状态 | 对齐时长降 · 三位一体脱节率 · 认领率 · cycle time | **北极星看板** | 产品负责人 | 飞书 OKR；bitable 看板（从节点状态自动汇总） |

> **§5 为什么要钦定**（回应"不够清晰"）：功能环节天然产出一堆（模块/spec/用户故事/验收/卡），下游研发不可能全盘看。**钦定"功能 spec 卡"为唯一真相源**——研发只认这张卡开 issue，其余都是它的附件/支撑。其它"产出多"的环节（§1、§8）同理钦定一件。

## 二·补 · 验证环节指标工具（采集 → 汇总回库 → 对照阈值）

> 框架一致：**各渠道用 API/导出把指标拉回 → 落 ezagent 库当「指标读数」(唯一真相源) → Metabase/飞书出看板对照 drop 阈值**。外部工具只当采集器/视图，不当真相源。

| 要量什么 | 渠道 | 工具（取 API/导出） | 选型说明 |
| --- | --- | --- | --- |
| 网页 使用量/漏斗/留存 | socialware 网页 | **PostHog**（自托管, MIT）/ 或 **ezagent 自身 telemetry** | PostHog=产品分析全家桶(事件/漏斗/留存/录屏)+API；最省则直接数 ezagent 已有 telemetry 事件 |
| 网页 PV/点击/来源 | 网页 / 自然流 | **Umami**（自托管, 轻量, MIT）/ Plausible | 埋一段 JS 就有 PV/UV/来源，看"自然流到了没"；Plausible 营销向更好看 |
| 小红书帖 阅读/互动 | 小红书 | 自己帖→**蒲公英 + 创作者后台导出**；大盘/竞品→**千瓜 / 新红(新榜有数)** | 小红书开放 API 仅对合作品牌开放；爬虫有合规风险不建议，自己帖走官方导出最稳 |
| 汇总成看板/对照阈值 | — | **Metabase**（自托管, 开源, 连库出看板+API）+ 飞书 bitable/OKR | Metabase 直连 ezagent 库出 drop 阈值看板；飞书 OKR 挂北极星（你已选） |

## 三、三条让它转起来的机制

1. **交接即 gate（类似 CI）**：每个箭头都是一次真相源交接；**上一环节的真相源没合格（没过自己的验收），下一环节不放行**。例：功能 spec 卡没写验收用例，不许开 issue。
2. **测试先行、绿才合（§7→§8）**：**测试用例不另写——就是 spec 卡的 Gherkin**；研发先把 Gherkin 写成测试代码（dev-loop `test-code-writer`），再写实现让它变绿（`test-runner`/`mix test`）。**测试不绿，不许提 PR / 不许合**。这把"验收"从一句话变成一道自动闸。
3. **只做该功能（§8 强约束）**：PR 必须只动该功能 spec 卡范围内的东西，**超范围（顺手美化/改无关页面）一律砍**；reviewer 过 gate 清单逐条勾（含"测试是否覆盖 spec 卡每条 Gherkin"），不过打回。这是把"每天 100+PR 收束到产品价值"的那道闸。
4. **不达标就 drop（§9）**：上线后渠道指标在窗口内未达阈值（如小红书帖 7 天阅读 < 500）→ **砍掉该功能子树的 PR/分支**，反哺回 §2 重选痛点。开发与验证错位（这周开发、下周验证）。

**贯穿纪律——三位一体**：每个开发节点（§6–§8）必带"产品跟进（spec）+ 运营跟进（changelog）"两个兄弟节点，谁缺谁显式"待分配"——杜绝"开发完才补产品运营"。

---

## 四、一句话收口

**这套流程 = 一条真相源接力链**：定位稿 → 痛点清单 → 认领映射 → 线框 → 功能卡 → issue → 测试 → PR → 指标，每一棒只接上一棒的一件东西、产出自己的一件交下去；**spec 卡的 Gherkin 一物三用**——既是验收、又是测试用例、又是 PR 过 gate 的判据；交接处是 gate、终点是 drop、全程三位一体 + 北极星量着转速。先在内部跑通（ezagent 第一个产品），适时开放外部。
