## 一句话定位（已拍板，全套据此收口）

**这是一个内部工具，同时它本身是 ezagent 的第一个产品**——先内部 dogfooding，适当时间再开放外部使用。

- **目的**：用 ezagent **规范 ezagent 团队自己的产品开发流程**，做到两件事——①让**价值闭环从根源就被跟踪**（从战略/定位出发，到痛点→体验→功能→开发→运营，每一步都挂在导图上、有人认领、有产物，谁也别脱节）；②让**每一个开发都有配合的产品和运营跟进**（开发/产品/运营三位一体耦合，不是开发完才补产品运营）。
- **dogfooding 的真实场景**：ezagent 团队用这个 workspace 来**开发 ezagent 面向不同用户群体的真实产品**。需求真实、高频、持续——不是为了演示自己造的假需求。
- **外部是后续阶段**：作为 ezagent 的第一个产品，先在内部把价值跑通，适时开放给外部团队。当前这套文档**只按内部场景写**，不做对外的 PMF 测分 / PLG 自助 / 差异化 vs Linear，这些一律标"待内部跑通后再议"。
- **底座** = ezagent（Elixir/OTP 消息路由 + 多 agent 编排运行时）。它长在 ezagent 自己的运行时上、能直接 dogfood 主线能力——这也是它作为"ezagent 第一个产品"最自然的形态。

形态一句话：思维导图当骨架（战略→开发→运营整条链收进一张活图）、每人一个 agent 当神经（替你盯认领的节点）、产物自动挂回节点当血肉（spec/PR/图归位）、一个网页出口让全队无会对齐。

## 当前确定性结论（已对齐，可据此开工）

1. **真相源永远在 ezagent 自己的库（默认 SQLite）**，外部工具都只是"能被 agent 自动读写的产物容器 + 协作面"，靠稳定 ID/URL/路径当外键挂回节点（`01-工具选型.md:17`）。
2. **进出只有两条铁路**：出站 external_mirror（`:push`/`:pull`）、入站统一 `Ezagent.Invocation.dispatch/1`（P14 铁律，不许 PubSub.broadcast 到入站 topic）。
3. **MVP 五块功能 + ICE 排序已定**：① 节点认领（P0 地基）② 产物挂载（P0，依赖①）③ 个人 agent 追踪（P1）④ 网页对齐出口（P1）⑤ 闭环看板（P2）（`04-spec与用户旅程.md:153`）。
4. **底座够用、只缺一个核心数据模型**：会话/agent/出口/权限/审计/飞书出入站都现成；唯独"思维导图 + 节点 + 认领 + 挂载"必须自研（最大块），GitHub 双向同步是第二大块。
5. **技术架构定型**：四柱一地基——地基=自研 mindmap domain；柱1=socialware public_view 出口；柱2=Entity.Agent+curl flavor；柱3=external_mirror 出站+入站 plugin；柱4=SQLite 真相源（`05-ezagent技术开发计划.md`）。
6. **MVP 边界明确不做**：world / agent-schema（在建未进 main，别压排期）、精细分租户、复杂结算、不自研导图编辑器（先 xmind 承载 + 关键结构镜进 workspace）。
7. **MVP 必须 vs 后置已分**：必须=节点认领+产物挂载(GitHub/飞书)+日spec/周闭环节奏+一条北极星+固定模板出口；后置=cc 重 flavor、动态编排器 UI、闭环看板、xmind/excalidraw/obsidian connector、PMF 引擎（`06-产品闭环与有效性评估.md` 第三部分）。
8. **北极星 + 哨兵指标已定**：北极星=周用户价值闭环数；四哨兵=周闭环数 + 对齐时长下降 + 挂载覆盖率 + cycle time，用来早警三种失败模式。
9. **方法论不是新发明**：Amazon PR/FAQ + Teresa Torres 机会-方案树 + RICE/ICE + Shape Up + Linear cycle/changelog + Superhuman PMF + Lean BML，七套验证过的方法缝成一张活图。

## 待验证 / 待决策项（开工前或开工中要解掉）

> 这些是文档里诚实标注 unverified、或机制评估里点名的高风险点。**不要当成已确定能力排期。**

**技术 unverified（`05` 风险表 R1–R10）**：
- **R1 页面树 schema 能力边界**——json-render 能不能渲染"导图/看板"这种复杂结构？撑不起就降级列表/表格视图（阶段 1 先实测）。
- **R4 节点建模成 Kind vs 普通记录**未定——影响并发/生命周期/LOC 预算，阶段 2 开工前要出一个 mini design。
- **R7 飞书文档变更事件能否订阅进 dispatch**未实测——不行就降级 agent 定期拉取。
- **R8 CapBAC 5 轴用于"节点认领"的语义匹配度**未验证——不够就在节点 slice 补认领元数据。
- **R9 curl flavor agent 能否被触发式"主动盯"**（节点变化→主动 notify）未实测——不行就 cron/定时 dispatch 唤醒。

**机制层最高不确定性（`06` 有效性评估）**：
- **个人 agent 是案例支撑最弱的差异化赌注**——没有现成公司做过完全一样的事。最大失效风险是 **agent 噪音**（N 个 agent 刷屏，对齐成本不降反升）和 **答不准**（和真相源漂移）。决策：MVP 先用最轻 curl flavor 验证"能追踪+能对话"且对齐时长真降，再决定是否放大/上 cc。
- **网页出口落地坑最多 + 依赖在建**——四坑（活会话同 BEAM / 字面布尔 true / SPA 必须 build / 编排器偏编排非画 UI）+ world 未进 main。决策：MVP 用固定模板视图兜底，动态 UI 后置。

**已知但仍需排期决策**：
- R5 GitHub Projects v2 必须走 GraphQL（REST 不够）——MVP 可先只做 issue/PR（REST 够），Projects v2 列后续。
- R3 LiveView 管理面有确定性测试失败 + 部分按钮坏——绕开用 HTTP API / iex RPC 建会话。
