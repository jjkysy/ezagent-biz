## 0 · 一句话先讲清"真相源在哪"

把这句记住，后面所有选型都围绕它转：

**真相源（source of truth）永远在 ezagent 自己的库里，外部工具都只是"能被 agent 自动读写的产物容器 + 团队协作面"。**

- 思维导图的"节点 ↔ 认领人 ↔ 产物链接"这张映射表，存 ezagent 自带库（默认 SQLite），不存在任何外部工具里。思维导图工具只负责"把树画出来"，认领和挂载状态是我们自己的领域数据。
- 每个外部工具里的东西（GitHub issue、飞书文档、excalidraw 文件）都有一个稳定的 URL / token / 文件路径。我们把这个稳定 ID 当外键，挂到对应节点上。
- 进出 ezagent 的方向是固定的两条铁路：
  - **出站**（把 ezagent 里的状态推到外部，或被外部按需拉）走 external_mirror 域，两种 KIND：`:push` 主动推 / `:pull` 被拉（`apps/ezagent_domain_external_mirror/lib/ezagent/external_mirror.ex:1`）。
  - **入站**（外部 webhook / 事件接回来）统一走 dispatch（铁律 P14，跨 Kind 唯一通路），照抄飞书插件的入站写法 `apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/inbound_dispatcher.ex:58`。
  - **网页出口**是 socialware——一个带 `public_view: true` 的 SessionTemplate，把"团队状态对齐面"暴露成一个公开会话，客户面 UI 由编排器 agent 动态生成（`.claude/skills/ezagent-socialware/SKILL.md`，控制器在 `apps/ezagent_web/lib/ezagent_web/controllers/socialware/`）。

判断一个工具能不能用，就两条硬标准：**(a) 它的产物有没有稳定 ID / URL / 文件路径能写进 ezagent 库？(b) agent 能不能自动读写它（建产物、查状态）？** 两条都满足才进推荐栈。

## 0.5 · 诚实分清"已交付"和"承诺式"（别把要自研的当成现成的）

俞军 review 命中一条：选型里好几块新体验是**承诺式、不是已交付**，混在一起会高估当前能力。本文按下面三档标注，每个工具决策末尾会写明它落在哪档：

- **【已交付】**：ezagent main 上已有、能直接用。例：飞书插件出入站（`apps/ezagent_plugin_feishu/`）、external_mirror 的 `:push`/`:pull` KIND、socialware 公开会话基础机制、`Entity.Agent` + 现成 curl/cc/codex flavor、dispatch（P14）。
- **【要自研】**：方案明确、但这套 workspace 要从零写的工程。例：节点↔认领↔产物的领域数据（最大块）、GitHub Projects v2 双向同步、飞书变更订阅入站、excalidraw/markmap 产物 connector。这些是 9.5 周排期的主体，**当前是计划不是能力**。
- **【在建·未进 main】**：ezagent 自己还没合并的能力，**不能当依赖**。例：world（新统一前端）、agent-schema（socialware SKILL §Future 明确标注）。涉及它们的地方必须有不依赖它的兜底路径。

**定位提醒（与 02 §〇收口一致）**：本套 workspace 当前定位=内部 dogfooding 工具，所有"网页出口对外公开""客户面 UI"等表述指的是**团队内部对齐面**，不是对外卖给别的团队的产品形态。

## 1 · 诉求点 → 工具决策（逐项展开）

下面按用户原始诉求逐条决策。每条给：**选什么 / 为什么 / 怎么跟 ezagent 接 / 风险与替代**。

### 1.1 思维导图（主载体：可认领、可挂产物、agent 实时读写）

- **选 markmap**（Markdown 真相源），xmind 退为导入/导出兼容格式。
- **为什么**：markmap 把**纯 Markdown**（`#`/`##` 标题 + `-` 列表）直接渲染成可交互思维导图（[markmap.js.org](https://markmap.js.org/)、[GitHub markmap/markmap](https://github.com/markmap/markmap)）。这意味着：
  - 节点 = Markdown 标题，天然有锚点 id；我们还能在节点行末加自定义标记（如 `<!-- node:positioning-01 owner:@alice -->`）当稳定 id + 认领人，agent 解析这一行就拿到"节点↔认领人"。
  - 产物挂载 = 在节点下挂一个 Markdown 链接（指向 GitHub issue / 飞书文档 / excalidraw 文件），markmap 直接渲染成可点击节点。
  - agent 追踪 = agent 直接读/改 Markdown，零额外 API（Claude 这类 agent 天生最擅长改 Markdown）。
  - 单一 `.md` 文件做真相源，没有多人文件冲突。
- **怎么跟 ezagent 接**：Markdown 真相源存 ezagent 库；`markmap-lib`（[文档](https://markmap.js.org/docs/packages--markmap-lib)）在 Node 端把 md 转成可嵌入 HTML/SVG，直接塞进 socialware 网页出口渲染。属于"我们自己的领域数据 + 网页出口渲染"，不走 external_mirror。**档位：渲染管线【要自研】（Node 端 md→HTML/SVG 嵌进会话面）。**
- **风险与替代**：风险是 markmap 只是渲染库、没有内置的"在线协作编辑器"，团队改图要走我们自己的会话编辑流或 git PR——这恰好符合"真相源在我们这"的设计，不是缺点。替代：mermaid mindmap（[语法](https://mermaid.js.org/syntax/mindmap.html)）只能做静态展示，严格树形不能跨分支连线，仅适合在某文档里嵌一张小图；Obsidian Canvas（`.canvas` JSON）能连边但要本地客户端、协作弱。**xmind 明确不做真相源**：它是本地文件、没有云端 REST API、多人同时改会文件冲突、agent 看不到实时变化（[xmindparser](https://github.com/tobyqin/xmindparser) 只能解析已上传的文件）。团队习惯 xmind 的话，初稿用它画，再转进 markmap，仅此而已。

### 1.2 框架补充图（架构图 / 线框图）

- **选 excalidraw**（`.excalidraw` 文件 + 自嵌 React 组件，必要时自托管）。
- **为什么**：`.excalidraw` 是纯文本 JSON（[JSON Schema](https://docs.excalidraw.com/docs/codebase/json-schema)），每个 element 有 id。agent 能直接生成这种 JSON，甚至先写 mermaid 再用官方 [`@excalidraw/mermaid-to-excalidraw`](https://docs.excalidraw.com/docs/@excalidraw/mermaid-to-excalidraw/api) 转成可编辑白板。官方 [`@excalidraw/excalidraw` React 组件](https://www.npmjs.com/package/@excalidraw/excalidraw) 可嵌进网页让团队在线编辑。
- **怎么跟 ezagent 接**：`.excalidraw` 文件存 ezagent 库，文件路径/id 当产物挂到思维导图的"具体开发/体验"节点；React 组件嵌进 socialware 网页出口。属于产物 connector（`docs/discuss/df-prd/03-思维导图.md` 6.6 节），自研。
- **风险与替代**：excalidraw.com 的官方协作房是端到端加密的临时房，状态不在我们这——**不要拿协作房做真相源**，要么自托管（开源可自部署），要么只用"文件 + 自己嵌的 React 组件"。替代：Figma 做高保真原型（设计岗已有的话），但 Figma 自动化弱、agent 难直接生成，只当人工原型工具、不进自动化链路。

### 1.3 开发追踪（issue + PR + 进度看板）

- **选 GitHub**（REST + GraphQL + webhook）。
- **为什么**：自动化能力是所有候选里最成熟的。issue/PR 有稳定 URL + number 直接当产物挂节点；issue 的 assignee 天然就是"认领人"，跟节点认领对齐；agent 用 GraphQL 拉"我 assignee 的 open issue / 待 review PR"就是"追踪自己的工作"。
- **怎么跟 ezagent 接**：
  - 出站走 external_mirror adapter（抄飞书 adapter 写法，`apps/ezagent_domain_external_mirror/lib/ezagent/external_mirror/adapter.ex`），把节点状态推成 issue / 评论。
  - 入站走 dispatch：GitHub webhook（issue/PR/project 变更）→ `Ezagent.Invocation.dispatch/1`（仿 `inbound_dispatcher.ex:58`）→ 更新对应节点状态，PR 合并 → 节点闭环。
  - **注意**：Projects v2 看板只能走 GraphQL（classic projects 已废弃），用 `updateProjectV2ItemFieldValue` 改 Status（[官方文档](https://docs.github.com/en/issues/planning-and-tracking-with-projects/automating-your-project/using-the-api-to-manage-projects)）。这是第二大块自研工程（`03-思维导图.md` 6.3 节）。**档位：GitHub API 成熟【已交付（外部）】，但双向同步 connector【要自研】——别把"GitHub 能力强"当成"我们已经接好了"。**
- **风险与替代**：风险是 GraphQL Projects v2 学习成本 + 别误用已废弃的 classic API。替代：`gh` CLI（[gh-pm 扩展](https://github.com/yahsan2/gh-pm)）让 agent 直接调命令行，作为脚本化兜底；纯 issue/PR 联动有社区成熟范式（[PR 改 issue status](https://medium.com/@martatatiana/github-projects-change-issue-status-based-on-pull-request-change-45dcacab9fb7)）。开发追踪基本非 GitHub 莫属。

### 1.4 产品文档 / spec

- **选飞书**（docx + 多维表格 bitable + 机器人）。Obsidian 退为"个人/技术向、跟 markmap 同源的本地 Markdown"场景。
- **为什么**：飞书云原生、实时多人协作、移动端齐全、国内团队接受度高，而且**ezagent 已经有现成飞书插件**（`apps/ezagent_plugin_feishu/`），出入站不用从零写。docx 有稳定 docToken、bitable 记录有 record_id，都能当产物挂载键；bitable 特别适合做"节点↔认领人↔产物"那张映射表的**团队可视镜像**。
- **怎么跟 ezagent 接**：
  - 出站走 external_mirror 复用飞书插件出站 `{FeishuAdapter, FeishuChatBinding}`（`apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/application.ex:120`），把 spec / 周报推进飞书群和文档。
  - 入站：订阅飞书文档/表格变更事件（如 `drive.file.bitable_record_changed_v1`）→ `inbound_dispatcher.ex:58` → dispatch → agent 实时追踪（[bitable 概述](https://open.feishu.cn/document/server-docs/docs/bitable-v1/bitable-overview?lang=zh-CN)、[创建文档 API](https://open.feishu.cn/document/server-docs/docs/docs/docx-v1/document/create?lang=zh-CN)）。**档位：飞书插件出入站【已交付】；但"订阅文档/表格变更事件"那条具体订阅【要自研】，且对应 05 风险表 R7（飞书变更订阅 unverified）——这是承诺式、未实测，开工先验。**
- **风险与替代**：风险是飞书 OpenAPI 鉴权有两类身份（tenant_access_token / user_access_token）、字段类型匹配有学习成本。替代：Obsidian（[Local REST API 插件](https://github.com/coddingtonbear/obsidian-local-rest-api) 还内置 MCP server，agent 能全量 CRUD）适合个人/技术成员、且能和 markmap 的本地 Markdown 同源——但它要本地开着客户端、团队协作靠 Sync 或 git、后台自动化偏重，**不做团队共享真相源**，只做个人辅助。

### 1.5 节点认领 + 产物挂载 + 个人 agent 追踪（这三条是同一套领域数据）

这三条诉求底层是**同一份 ezagent 领域数据**，不是三个外部工具，所以放一起。

- **数据真相源选 ezagent 自带 SQLite**。
  - **为什么**：节点↔认领人↔产物链接的映射、每个 agent 的追踪状态，都是结构化、单实例、读多写适中的数据，SQLite 完全扛得住，而且零运维、跟现有领域数据同一张库同一个事务。
  - **怎么接**：建成新的领域数据——节点 = Kind，认领 = Grant，挂载 = slice + 附件（`docs/discuss/df-prd/03-思维导图.md` 6.1 节，最大块自研）。写走 Behavior 的 `{:set, key, value}` effect，读走框架注入的 `ctx[:read]`，**不直接碰存储**（守 Behavior 契约）。**档位：SQLite 存储【已交付】，但节点↔认领↔产物这套领域数据本身【要自研】（最大块）。**
  - **风险与替代**：撞到这三个信号之一再迁 Postgres——① 多节点分布式部署/高并发写；② 要存大量全文/向量做语义检索（Postgres + pgvector）；③ 重报表分析查询。现在都不满足，**先别上外部数据库**。
- **个人 agent 选 ezagent `Entity.Agent` + flavor**。
  - **为什么 / 怎么接**：每人 spawn 一个统一 agent 实例 `entity://<ws>/agent/<人名>`，flavor 决定装哪套行为（`apps/ezagent_domain_agent/lib/ezagent/entity/agent.ex:1`，base_behaviors 在 `:86`）。它"追踪某人的工作"= 读"挂在该人认领节点下的产物记录" + 调外部工具 API 拉最新状态；agent 间对话走会话域 + dispatch。MVP 用轻量 curl flavor 验证"能追踪 + 能对话"，cc flavor 按需上（`03-思维导图.md` 6.2 节）。
  - **风险与替代**：风险是 agent 数量随团队人数线性增长的资源管理，MVP 团队 3–10 人无压力。无外部替代——这是 ezagent 的核心卖点，不外包。**档位：`Entity.Agent` + 现成 flavor【已交付】，但"个人 agent 能降对齐成本而非制造噪音"是【最高不确定性赌注·待验证】。** 俞军 review 命中：这是整套设计成败所系的最致命假设，自标"案例支撑最弱"。**验收必须验"价值兑现"不只"功能可用"**——不是"能追踪+能对话"就算过，而是 05 阶段 1 用最小 curl flavor、3-5 人、2 周实测"对齐时长真的降了"；降了再往下，没降就停，把 9.5 周风险压到 2 周。**唯一的真新体验恰恰最没把握兑现，必须最先证伪。**

### 1.6 网页出口（一页看全队状态）

- **选 socialware**（带 `public_view: true` 的 SessionTemplate + 编排器 agent 动态生成 UI）。
- **为什么**：这是 ezagent 把会话公开成网页的现成机制。一个 socialware app **本质就是一个 `public_view` 的 SessionTemplate**（`.claude/skills/ezagent-socialware/SKILL.md`，`session_template.ex:719`，fail-closed 在 `public_view.ex:38`）。客户面 UI 由编排器 agent 一轮轮组合（React + json-render，不是手写 HEEx），匿名旁观者也能看。
- **怎么跟 ezagent 接**：把 markmap 渲染 + 各产物状态 + 闭环看板聚合进这个公开会话面，编排器把团队状态组成页面树喂 Surface（`Surface.put_version(turn_id, tree)` + `approve`），客户端 SPA 渲染。访问入口 `/socialware/chat?session_uri=…`（控制器 `apps/ezagent_web/lib/ezagent_web/controllers/socialware/`）。
- **风险与替代**：风险有两个——① 编排器现有 9 个工具偏"编排团队"而非"画任意 UI"（`tool_catalog.ex`），复杂可视化可能要补工具或退回固定模板视图；② **world（新统一前端）和 agent-schema 在建、未进 main**，别当已有能力依赖（SKILL §Future）。替代/兜底：先用固定页面树模板把核心状态（认领率、产物挂载、对齐时长趋势）渲染出来，等 world 落地再升级动态 UI。**档位：socialware 公开会话基础机制【已交付】；动态 UI 依赖的 world/agent-schema【在建·未进 main，不能当依赖】，故 MVP 先走固定模板兜底。** **定位提醒**：这个"网页出口"是**团队内部对齐面**（自己人打开看全队状态），不是对外卖的客户产品；§0.5 已把对外形态划走。

| **外部 ↔ ezagent 进出**（贯穿） | **入站 dispatch（P14）/ 出站 external_mirror** | 所有 webhook 入站统一 dispatch，出站镜像统一 external_mirror | 入站仿 `inbound_dispatcher.ex:58`；出站 `:push`/`:pull` adapter | 铁律不能绕（PubSub 直推 inbound=事故 2.1 根因） |

## 3 · 落地优先级（一句话）

**第 0 步先验最致命赌注，再谈接工具**：05 阶段 1 用最小 curl flavor、3-5 人、2 周实测"个人 agent 能不能真降对齐时长"——这是整套设计成败所系（俞军 review 核心结论），降了再往下，没降就停。**先接 GitHub + 飞书两条最成熟、且飞书插件 ezagent 已有的链路**；思维导图先用 markmap 的 Markdown 真相源 + 关键结构落进 ezagent 库；网页出口先用 socialware 固定模板视图把核心状态（认领率/挂载覆盖/对齐时长趋势）显出来，等 world 落地再升级动态 UI。xmind / Obsidian 因"本地文件、无云 API、协作弱"全退为兼容/个人场景，**不做团队真相源**。真相源始终在 ezagent 库，外部工具都是可被 agent 自动读写的产物容器。**全程定位=内部 dogfooding 工具（与 02 §〇一致），不做对外 PMF/PLG/差异化叙事。**
