## 第一部分 · 产品 Spec(MVP)

### 关于优先级打分（用 ICE）

MVP 阶段团队就是我们自己，触达人数（RICE 里的 Reach）这一维度区分度低、还得拍脑袋估，所以这里用 **ICE**（Impact 影响 / Confidence 信心 / Ease 易实现），三项各 1–10 分，总分 = 三项相乘 / 100（归一到 0–10，越大越先做）。ICE 出自 Sean Ellis / GrowthHackers，对比见 https://www.productlift.dev/blog/rice-vs-ice 。

每个功能点同时贴一张"挂钩牌"（对应思维导图 8.6 `03-思维导图.md:210`）：服务哪个痛点 / 拨动哪个北极星输入指标 / 闭环判据，让 spec 不悬空。

### 关于用户价值公式（评审整改 4：ICE 只算开发成本，不算用户支付成本，是用户价值核算失真的根）

俞军方法论评审指出：本 spec 原来每个功能只有 ICE（开发侧）和挂钩牌，**没算用户为用上它要付的非货币代价**。现在每个功能强制加一张**价值卡**，按 **用户价值 = 新体验 − 旧体验 − 替换成本** 回答三问：

- **给谁创造了什么真实价值**（新体验 − 旧体验）：哪类用户、在哪个情境（A=我们自己内用 / B=对外卖，旧体验天差地别）、原来花 X 现在花 Y 的真实差额。
- **用户非货币支付/替换成本**：学习成本（新心智模型）+ 迁移成本（已在 Linear/Notion/飞书的数据与肌肉记忆）+ 运维成本（自己跑 BEAM/SPA build/双向同步）+ 信任成本（agent 答不准比没有更坏）。
- **净值判定**：套损失厌恶 2.5×，价值要 > 替换成本的 2.5 倍才成立。

**情境收口（评审整改 1）**：本 spec 锚定**情境 A（纯内部 dogfooding 工具）**——对一个真实用户（我们自己）做实净值为正。情境 B 的对外动作不写进 MVP 承诺，待情境 A 验证后再启。

### 功能 1 · 节点认领（思维导图 + 责任绑定）

服务体验承诺 4.1「一张图看懂产品」+ 4.2「每个节点都有主」（`03-思维导图.md:72`）。

**用户故事**
- 作为产品，我想在导图的某个分支下新建一个功能点节点并认领它，这样这件事就有了明确的主和位置。
- 作为任一成员，我想看到没人认领的节点被显式标成"待分配"，这样责任不会无声烂掉。
- 作为负责人，我想看到每个节点的状态（待分配 → 已认领 → 进行中 → 已闭环）流转，这样我知道哪里卡住。

**验收标准**
1. 能在根 + 六层第一分支（定位/痛点/体验/功能/开发/运营）下增删节点、挂子节点。
2. 节点能被一个人认领，认领后绑定责任人（人 = `Ezagent.Entity.User`，`apps/ezagent_domain_identity/lib/ezagent/entity/user.ex`）。
3. 未认领节点显式显示"待分配"，导图里不存在"既没认领也没标待分配"的灰色节点。
4. 状态机四态可流转，状态变更落 ezagent 库（真相源 SQLite，`research/B-工具选型调研.md:147`）。

**落地要点（ezagent）**
节点 = 新 domain 里的一个领域模型（Kind），认领 = 把 User 绑到节点，状态写用 `{:set, key, value}` effect、读用 `ctx[:read]` reader（Behavior 契约见 `.claude/skills/ezagent-developer/references/new-contract.md`）。**这是最大块自研**——ezagent 现成没有"图/节点"概念（`research/A-ezagent能力盘点.md` §5）。导图本体 MVP 先用 XMind（https://xmind.app/ ）承载初稿、关键结构镜进 workspace（Markdown/markmap 真相源，`research/B-工具选型调研.md:43`）。

**价值卡（用户价值公式）**
- 给谁：情境 A 全队，每个认领人。
- 真实价值（新体验 − 旧体验）：旧体验=责任靠口头/群里默认，常无声烂掉；新体验=节点必被认领、未认领显式"待分配"，"这事归谁/做到哪"一眼可查，省掉刷群问进度。差额=对齐时长↓ + 漏接↓。
- 用户非货币支付/替换成本：学习成本=一套"节点状态机/认领=Grant"心智（中）；迁移成本=情境 A 几乎为零（无历史工具沉淀要搬，这是替换成本远低于情境 B 的关键）；运维/信任成本≈0。
- 净值判定：替换成本低（无迁移）、价值真实 → **情境 A 下净值正，过 2.5× 线**。（情境 B 因迁移成本极高，本功能不锚定对外。）

**挂钩牌**：服务痛点 2.1 战略执行脱节 → 拨动「节点认领率」（北极星输入 A）→ 闭环判据：节点能认领、状态能流转、未认领显式标记。

**ICE**：Impact 9（整个产品的骨架，没它别的都挂不上）· Confidence 7（要自研但机制清楚）· Ease 4（最大块自研工程）→ **2.52**。优先级 **P0**（地基，必须最先做）。

### 功能 2 · 产物挂载（各工具产出 → 挂回节点）

服务体验承诺 4.3「产物自动归位」，对治痛点 2.2 产物散落（`03-思维导图.md:81`）。

**用户故事**
- 作为研发，我在 GitHub 开了 issue/PR 后，希望它的链接自动挂回对应节点，不用手动贴。
- 作为产品/运营，我在飞书写完 spec 文档后，希望文档自动挂回节点。
- 作为任一成员，我想从一个节点点进去就看到它下面挂的所有产物（带类型 + 来源 + 时间）。

**验收标准**
1. 一个节点能挂多类产物，每条产物记录类型 + 来源 + 时间戳。
2. 挂载键稳定：GitHub issue/PR URL、飞书 docToken、excalidraw 文件路径，全部落 ezagent 库映射。
3. MVP 至少跑通 **GitHub + 飞书** 两个挂载来源（产物挂载覆盖率可统计）。
4. 在任一支持的外部工具里产出后，节点页能看到该产物条目。

**落地要点（ezagent）**
用 external_mirror 域做出站镜像 / 双向链接（`apps/ezagent_domain_external_mirror/lib/ezagent/external_mirror/adapter.ex`），它本就有 `:push`（推到外部）和 `:pull`（被外部拉）两种 KIND。飞书 adapter **现成抄即用**（`apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/application.ex:120`）；挂载本身 = 把外部产物引用写进节点 Kind 的 slice。

**价值卡（用户价值公式）**
- 给谁：情境 A 全队，尤其"找东西的人"。
- 真实价值：旧体验=图在 xmind、代码在 GitHub、文档在飞书，找东西翻五个地方；新体验=节点变唯一索引，点一个节点看全产物。差额=查找时间↓。
- 用户非货币支付/替换成本：运维成本（高且承诺式）——GitHub/飞书双向同步是自研两大块、R7 飞书变更订阅 unverified，**这个价值当前是承诺式、未交付**；信任成本=同步漏挂会让"唯一索引"破功。
- 净值判定：价值真实但**净值待兑现**——必须以 GitHub+飞书两来源实跑兑现，否则替换成本（运维）会吃掉价值。

**挂钩牌**：服务痛点 2.2 产物散落 → 拨动「产物挂载覆盖率」（北极星健康度）→ 闭环判据：GitHub + 飞书两来源能挂、能从节点点开。

**ICE**：Impact 8（节点变成唯一索引，"找东西翻五个地方"被解决）· Confidence 6（飞书现成、GitHub 要自研）· Ease 5 → **2.40**。优先级 **P0**（和功能 1 并列地基，但依赖功能 1 先有节点）。

### 功能 3 · 个人 agent 追踪（每人一个 agent + 互相对话）

服务体验承诺 4.4「有个 agent 替你盯」，对治痛点 2.3 对齐成本高（`03-思维导图.md:85`）。

**用户故事**
- 作为任一成员，我想有一个长期存在的个人 agent，随时能问它"我认领的节点进度如何"。
- 作为运营，我想让我的 agent 去问研发的 agent"这个功能这周能上吗"，不用反复去群里 @人。
- 作为成员，我想 agent 在我认领的节点有变化（如 PR 合并、状态流转）时主动提醒我。

**验收标准**
1. 每人 spawn 一个长期个人 agent，地址形如 `entity://<ws>/agent/<人名>`。
2. agent 能读"自己认领的节点"并回答进度问题。
3. agent 之间能在会话里对话（跨人协调），agent 与人平等参会（`docs/discuss/intro/02-领域层全览.md:58`）。
4. MVP 用轻量 curl flavor 验证"能追踪 + 能对话"即可，重 agent（cc flavor）按需上。

**落地要点（ezagent）**
`Ezagent.Entity.Agent` + flavor（`apps/ezagent_domain_agent/lib/ezagent/entity/agent.ex`，flavor 装配在 `:86`）。flavor 可选 cc（跑真 Claude Code CLI）或 curl（HTTP LLM，如 DeepSeek）；加新口味抄 plugin 模式（`apps/ezagent_core/lib/ezagent/plugin.ex:186`）。实测路径见 `docs/discuss/intro/04-如何使用ezagent.md`。

**价值卡（用户价值公式）—— 唯一真新体验，也是最高不确定性赌注**
- 给谁：情境 A 全队。
- 真实价值：旧体验=反复 @人/开会问"做到哪了"；新体验="问人"变"问 agent"，对齐时长直接降——**这是全套材料唯一可能的真新要素，但价值未经实测**。
- 用户非货币支付/替换成本：信任成本（高）=agent 答不准"比没有 agent 更坏"（材料自承）；学习成本=与 agent 平等参会的新交互。
- 净值判定：**未验证**——评审（decision）指出"最该先证伪的价值假设，9.5 周排期里没一个阶段正面验"。整改：把"对齐时长真的下降"提为阶段 1 硬验收（见下文验收 + `05` 阶段 1），3–5 人用 2 周实测，降了再往下、没降就停。预期效用=（收益×成功概率 − 成本），赌注自标"最高不确定性"=概率低，不前置验证就投满 9.5 周，期望值可能为负。

**挂钩牌**：服务痛点 2.3 对齐成本高 → 拨动「对齐时长下降」（北极星健康度）→ 闭环判据：**对齐时长实测下降 X%**（不是"能追踪+能对话"的功能可用性，而是价值兑现）+ 一个 agent 能答"我认领节点进度如何" + 跨 agent 能对话一轮。

**ICE**：Impact 8（"问人"变"问 agent"，对齐成本直接降）· Confidence 7（Entity.Agent + curl flavor 是现成机制）· Ease 6 → **3.36**。优先级 **P1**（差异化核心，地基功能 1/2 落地后紧接做）。**注**：ICE 的 Confidence 7 只评"技术能搭出来"，**不等于"价值能兑现"——价值置信度低，须靠阶段 1 实测兑现。**

### 功能 4 · 网页对齐出口（一页看全队状态）

服务体验承诺 4.1/4.2，是团队对齐的单一触点（`03-思维导图.md:106`）。

**用户故事**
- 作为任一成员，我想打开一个网页就看到整张图当前状态：谁认领了什么、各节点挂了哪些产物、进度、本周闭环数。
- 作为旁观者（未注册），我想打开分享链接就能只读看到对齐面，不必登录。
- 作为负责人，我想用这一页替代"开会同步 + 刷群问进度"。

**验收标准**
1. 一个网页展示整张导图当前状态（认领情况 / 各节点产物 / 进度 / 本周闭环数）。
2. 匿名访客打开 `/socialware/chat?session_uri=…` 能看到聚合状态（编排器吐页面树）。
3. 会话在服务节点内活着（`public_view?/1` 读活会话 slice，`apps/ezagent_domain_socialware/lib/ezagent/socialware/public_view.ex:38`，fail-closed）。
4. 客户 SPA 已 build（`cd apps/ezagent_web/assets && pnpm install` + `mix assets.build`），否则空白页。

**落地要点（ezagent）**
socialware 公开会话面 = 一个带 `public_view: true` 的 SessionTemplate（`apps/ezagent_domain_session/lib/ezagent/entity/session_template.ex:719` 登记 `public_view` 内容键）。**界面由编排器 agent 动态生成**（React + json-render，非手写 HEEx，`.claude/skills/ezagent-socialware/SKILL.md` §"Two surfaces a socialware app exposes"）——所以"显示什么状态"由编排逻辑灵活组织。匿名生命周期全自动（铸匿名用户 / 下 cookie / 加入会话，同 SKILL §"Step 3"）。
⚠️ 三坑：会话必须在服务节点活着（不然 302 到 /login）；`public_view` 现在没 UI 开关、只能内容/CLI 设；SPA bundle 不 build 则 200 但空 DOM（同 SKILL §"Load-bearing gotchas"）。

**价值卡（用户价值公式）**
- 给谁：情境 A 全队 + 负责人。
- 真实价值：旧体验=晨会同步 + 刷群问进度；新体验=一页看全队状态，无会对齐。差额=对齐时长↓（最直接可量的省时）。
- 用户非货币支付/替换成本：运维成本（中）=自己跑 BEAM 服务节点活会话 + SPA build，三坑（302/无 UI 开关/空 DOM）不踩才有页。
- 净值判定：情境 A 内运维成本自担可接受、价值真实 → **净值正**。

**挂钩牌**：服务痛点 2.3 对齐成本高 + 2.1 脱节 → 拨动「对齐时长下降」→ 闭环判据：匿名访客打开链接能看到聚合状态。

**ICE**：Impact 9（对齐的唯一触点 + 对外展示面）· Confidence 6（socialware 原语在 main，但有三坑）· Ease 5 → **2.70**。优先级 **P1**（功能 1/2 有数据后才有东西可展示）。

### 功能 5 · 闭环看板（dogfooding 节奏可视化）

服务痛点 2.4 迭代慢 + 北极星（`03-思维导图.md:111`）。

**用户故事**
- 作为产品/运营，我想看到一个看板：今天 spec 出了没、本周闭了几个用户价值环、本周运营策略调了没。
- 作为负责人，我想看板指标从节点状态自动汇总，不用手工统计。

**验收标准**
1. 看板显示"今日 spec 出没出 / 本周闭了几个环 / 运营调没调"。
2. 指标自动从节点状态机（功能 1）汇总：已闭环节点计数、本周新增 spec 数等。
3. 周报能经 external_mirror 镜到飞书群。

**落地要点（ezagent）**
看板是网页出口（功能 4）的一个视图；数据从节点状态机（功能 1）汇总；周报出站走 external_mirror 镜到飞书（复用功能 2 的飞书 adapter）。

**价值卡（用户价值公式）**
- 给谁：情境 A 产品/运营/负责人。
- 真实价值：旧体验=进度靠手工统计、节奏不可见；新体验=节奏可见、倒逼速度，指标自动从节点状态汇总。差额=统计时间↓ + 节奏可控。
- 用户非货币支付/替换成本：低（建在功能 1/4 之上、纯汇总，无新心智、无新运维）。
- 净值判定：**净值正但不阻塞**——锦上添花，不是地基。注：北极星应以「对齐时长下降」为主结果指标，「周闭环数」是"自己数闭环"的活动指标，看板需并列展示对齐时长降幅（评审整改 9）。

**挂钩牌**：服务痛点 2.4 迭代慢 → 拨动「对齐时长下降」（主结果）+「周用户价值闭环数」（活动指标）+「日 spec 产出率」→ 闭环判据：看板能显示三个 dogfooding 指标。

**ICE**：Impact 7（让节奏可见、倒逼速度，但不阻塞别的功能）· Confidence 7（建立在功能 1/4 之上、纯汇总）· Ease 6 → **2.94**。优先级 **P2**（功能 1+4 落地后顺势做）。

## 第二部分 · 关键角色用户旅程（User Journey）

四个角色各一条端到端旅程。每步给：**步骤 / 触点（在哪个界面或工具）/ 情绪 / 对应系统动作（ezagent 在背后干了什么）**。

> 贯穿主线（所有角色共享）：打开网页出口 → 看导图认领节点 → 在对应工具产出产物并挂载 → 个人 agent 追踪+提醒 → 团队对齐 → 完成价值闭环。

---

### 角色 A · 产品（认领 定位/痛点/体验/功能 层）

| 步 | 步骤 | 触点 | 情绪 | 系统动作（ezagent） |
|---|---|---|---|---|
| 1 | 早上打开网页出口，扫一眼全队状态、找今天该推的功能点 | `/socialware/chat?session_uri=…`（功能 4） | 想快速进入状态、有掌控感 | socialware `public_view?/1` 放行匿名/已登录访问，编排器 agent 吐出聚合页面树 |
| 2 | 在"功能"分支下新建一个功能点节点并认领 | 网页出口导图视图 / XMind 初稿 | 有的放矢、责任清晰 | 节点 Kind 新建 + 把自己（`Entity.User`）绑为责任人，状态置「已认领」，`{:set}` 写库 |
| 3 | 写 spec 文档，挂回该节点 | 飞书 docx（https://www.feishu.cn/product/doc ）/ Obsidian | 顺手、不跳工具 | external_mirror 把飞书 docToken 作为产物挂回节点（功能 2，飞书 adapter 现成） |
| 4 | 个人 agent 提醒"这个节点研发还没认领开发子节点" | 个人 agent 会话 | 安心、不用自己盯 | 个人 agent（`Entity.Agent` curl flavor）读自己认领节点、检测到下游悬空 → notify |
| 5 | 让我的 agent 去问研发的 agent"这周能排上吗" | agent 间会话 | 省去当面催 | 两 agent 平等参会对话（`docs/discuss/intro/02-领域层全览.md:58`），结论回写节点 |
| 6 | 周末看这个节点是否"闭环"，确认能写进 changelog | 闭环看板（功能 5） | 成就感、节奏感 | 看板从节点状态机汇总"本周闭环数"，节点走到「已闭环」 |

**价值闭环达成信号**：该功能节点状态走到「已闭环」且这周 changelog 能写出一条用户可感知价值（对应北极星，`03-思维导图.md:222`）。

### 角色 B · 研发（认领 具体开发 层）

| 步 | 步骤 | 触点 | 情绪 | 系统动作（ezagent） |
|---|---|---|---|---|
| 1 | 打开网页出口，看哪个功能节点已 spec、等开发 | `/socialware/chat?…`（功能 4） | 清楚知道该做什么 | 编排器吐页面树，标出「已认领但开发子节点待分配」的功能 |
| 2 | 在功能节点下新建"开发"子节点并认领 | 网页出口导图视图 | 责任明确 | 节点 Kind 新建 + 绑研发为责任人，状态「已认领」 |
| 3 | 开 GitHub issue / 提 PR，assignee = 自己 | GitHub（https://github.com/ ） | 在熟悉工具里干活 | external_mirror 入站 webhook 经 `Ezagent.Invocation.dispatch/1`（P14 铁律，仿 `inbound_dispatcher.ex:58`）把 issue/PR 事件接回，挂回节点（功能 2） |
| 4 | PR 合并，节点状态自动从「进行中」转「已闭环」 | GitHub webhook → 节点 | 不用手动改状态、爽 | webhook 事件 dispatch → Behavior 把状态 `{:set}` 成「已闭环」，产物挂载覆盖率 +1 |
| 5 | 个人 agent 提醒"你认领的节点 X CI 挂了" | 个人 agent 会话 | 及时、不漏 | 个人 agent 读自己认领节点的产物状态变化 → notify |
| 6 | 在网页出口确认本周这条价值环已闭、对齐无需开会 | 闭环看板（功能 5） | 轻松、节奏稳 | 看板汇总，会话在服务节点活着供匿名对齐 |

**价值闭环达成信号**：建 issue → 挂节点、PR 合并 webhook → 更新节点状态，整条闭环跑通（对应 `03-思维导图.md:140`）。

### 角色 C · 运营（认领 营销/运营 层）

| 步 | 步骤 | 触点 | 情绪 | 系统动作（ezagent） |
|---|---|---|---|---|
| 1 | 打开网页出口，看本周哪些功能将闭环、可写进 changelog | `/socialware/chat?…`（功能 4） | 提前规划、不被动 | 编排器吐"本周闭环候选"视图 |
| 2 | 在"运营"分支认领一个策略节点（如本周 changelog） | 网页出口导图视图 | 责任清晰 | 节点 Kind 新建 + 绑运营，状态「已认领」 |
| 3 | 写每周 changelog + PMF 周测分，挂回节点 | 飞书 docx + bitable（多维表，https://www.feishu.cn/product/base ） | 顺手沉淀 | external_mirror 把飞书 docToken / record_id 挂回节点（功能 2） |
| 4 | changelog 经镜像发到飞书群 | 飞书群 | 触达团队/用户、省事 | external_mirror `:push` 把周报镜到飞书群（功能 5） |
| 5 | 个人 agent 提醒"PMF 分低于 40% magic 线，需补短" | 个人 agent 会话 | 有方向盘、不抓瞎 | 个人 agent 读 PMF 产物 + 阈值 → notify（PMF 方法见 Superhuman https://review.firstround.com/how-superhuman-built-an-engine-to-find-product-market-fit/ ） |
| 6 | 据 PMF 分决定本周加固/补短，调整运营策略并标执行 | 网页出口 + 闭环看板 | 闭环、有掌控 | 节点状态流转，看板「周运营调整执行率」+1 |

**价值闭环达成信号**：本周 changelog 至少一条用户可感知价值 + PMF 已测 + 运营策略据此调整且执行（对应 `03-思维导图.md:166`）。

### 角色 D · 负责人（定表 + 全局对齐 + 押注）

| 步 | 步骤 | 触点 | 情绪 | 系统动作（ezagent） |
|---|---|---|---|---|
| 1 | 打开网页出口，一页看全队状态替代晨会 | `/socialware/chat?…`（功能 4） | 省时、全局掌控 | socialware 聚合面，匿名也可看，编排器吐全局页面树 |
| 2 | 定"岗位 ↔ 层 ↔ 工具 ↔ 产物"映射表，确认无悬空分支 | 飞书 bitable（功能 1 派生） | 边界清晰 | 节点认领率从状态机实时算出，未认领节点显式「待分配」 |
| 3 | 看到某节点长期「待分配」或卡「进行中」，指派/介入 | 网页出口导图视图 | 及时发现风险 | 节点状态机暴露停滞节点；负责人改责任人 `{:set}` 写库 |
| 4 | 让自己的 agent 汇总"本周北极星 + 三个输入指标" | 个人 agent 会话 | 数据驱动、不靠感觉 | 个人 agent 读看板汇总数据回答（周闭环数 / 认领率 / cycle time） |

| 6 | 每 4–6 周结一个押注、回看北极星、重塑机会树 | XMind/markmap 重塑版 + 飞书下注会纪要 | 战略上有节奏 | 机会树重塑回填进 workspace（Shape Up 断路器 https://basecamp.com/shapeup/2.3-chapter-09 ） |

**价值闭环达成信号**：每周期末有有意义成品、北极星动向已复盘、机会树已回填（对应 `03-思维导图.md:231`）。

## 第三部分 · 主线串一句话

四个角色走的是同一条路：**打开网页出口对齐 → 在导图认领自己那层的节点 → 在最顺手的工具产出产物并自动挂回节点 → 个人 agent 替你盯进度并跨 agent 协调 → 看板/出口让团队无会对齐 → 节点走到已闭环 = 一个用户价值闭环**。每天闭一小步（叶节点 spec）、每周闭 1–2 个价值环、每 4–6 周结一个押注重塑树——整张思维导图就这么转起来，自己用自己（dogfooding），北极星「周用户价值闭环数」就是这台发动机的转速表。
