## 第一部分 · 端到端产品闭环 SOP（可执行版）

### 1.0 先记住整台发动机一句话

战略用 PR/FAQ 说清给哪个用户群体解决什么、定北极星（**根源价值跟踪率 + 三位一体覆盖率 + 返工下降**）→ 思维导图（机会-方案树）把它拆成有挂钩牌的叶节点，**每个开发节点都强制配上对应的产品节点和运营节点（三位一体）** → 每周一下注会选 1-2 个押注 → 每天产 spec、做一小块、产物挂回节点，**开发推进的同时产品和运营节点同步认领、同步推进** → 全队用这个 workspace 开发 ezagent 真实功能、把难受当场变新节点 → 每周发 changelog 让全队对齐 → 周日收指标看根源跟踪/三位一体覆盖/返工动没动 → 每 4-6 周回看北极星、重塑机会树回填战略，转下一圈（完整串联见 `02-战略到ROI闭环与案例.md:151`）。**当前阶段的"用户"就是 ezagent 团队自己，不掺对外动作。**

承载这一切的是 ezagent 三件套：**每人一个 agent 盯节点**（`apps/ezagent_domain_agent/lib/ezagent/entity/agent.ex`，base_behaviors 在 `:86`）、**external_mirror 把产物挂回节点**（`apps/ezagent_domain_external_mirror/lib/ezagent/external_mirror/adapter.ex`）、**socialware 一个网页出口让全队对齐**（`.claude/skills/ezagent-socialware/SKILL.md`，`apps/ezagent_domain_socialware/lib/ezagent/socialware/public_view.ex:38`）。

### 1.1 SOP 七步（每步：触发条件 → 动作 → 责任岗位 → 工具触点 → 产出 → 通过判据/指标）

把 02 篇的 ①~⑧ 八环节压成可照着干的七步 SOP（⑦ROI 和 ⑧反哺合到"收口"一步）。每一步都写清"什么时候做、谁做、动完算不算数"。

#### 步骤 S1 · 立战略（触发：项目启动 / 每 4-6 周期初）

| 项 | 内容 |
|---|---|
| 触发条件 | 项目第一次启动；或每个 4-6 周押注周期开头 |
| 动作 | 写一份 PR/FAQ（假新闻稿 + 5 页内 FAQ），定 1 个北极星 + 3-5 个输入指标 |
| 责任岗位 | 产品负责人 |
| 工具触点 | 飞书 docx（PR/FAQ）+ 飞书 bitable（指标定义） |
| 产出 | PR/FAQ 定稿；北极星 + 输入指标口径表。**内用阶段北极星 = 三个真结果指标：① 根源价值跟踪率（开发节点能往上追到战略/定位的比例）② 三位一体覆盖率（有配套产品+运营节点的开发节点比例）③ 返工下降（因没对齐/没挂钩牌而推倒重做的事件减少）**。输入指标：认领率 / cycle time / 日 spec 产出率 / 对齐时长 / 挂载覆盖率。「周价值闭环数」降为**活动指标，不当北极星**——见下方诚实提示 |
| 通过判据 | PR/FAQ 评审过一轮；北极星是领先指标、人话能讲清、不是虚荣指标（Amplitude 北极星 https://amplitude.com/books/north-star/about-north-star-framework ；Amazon PR/FAQ https://workingbackwards.com/concepts/working-backwards-pr-faq-process/ ）。**诚实提示（俞军评审命中）**："周闭环数"是**自己给自己数的活动指标，伪装成结果指标**——活动量涨不等于价值兑现。所以内用阶段把北极星钉在三个能反映"根源被跟踪 + 三位一体推进 + 少返工"的结果上（根源跟踪率 / 三位一体覆盖率 / 返工下降），它们直接对应这个产品要解决的两个根本问题（价值从根源跟踪、开发产品运营不脱节）。**对外动作（第一个非自己团队是否愿用）是后续阶段的事，本阶段不据此判价值。** |

#### 步骤 S2 · 拆导图（触发：战略定稿后 / 探索访谈带回新机会）

| 项 | 内容 |
|---|---|
| 触发条件 | S1 战略定稿；或任何时候探索访谈带回真实痛点 |
| 动作 | 搭机会-方案树：痛点→方案→叶节点，每个叶节点贴"挂钩牌"（挂哪个痛点 / 拨哪个输入指标 / ICE 分 / 验证假设 / 闭环判据） |
| 责任岗位 | 产品定结构；各岗位认领自己那层（岗位↔层映射见 `03-思维导图.md:62`） |
| 工具触点 | xmind 画初稿 → markmap Markdown 当真相源（节点=标题有锚点 id）；挂钩牌落飞书 bitable；真相源映射存 ezagent 库（SQLite，`01-工具选型.md:73`） |
| 产出 | 一棵连通无孤儿的树；每个叶节点挂钩牌填齐；节点↔认领人↔产物映射进 ezagent 库（节点=Kind，认领=绑 `Ezagent.Entity.User`，写用 `{:set,key,value}` effect、读用 `ctx[:read]`，契约见 `.claude/skills/ezagent-developer/references/new-contract.md`） |
| 通过判据 | 每个叶节点能往上追到一个真实痛点（树连通）；每个叶节点挂钩牌齐（机会-方案树 https://www.producttalk.org/opportunity-solution-trees/ ；ICE https://www.productlift.dev/blog/rice-vs-ice/ ） |

#### 步骤 S3 · 下注选题（触发：每周一）

| 项 | 内容 |
|---|---|
| 触发条件 | 每周一固定 30 分钟下注会 |
| 动作 | 从叶节点里按 ICE 分排序，挑本周 1-2 个押注（是"押注"不是"无限 backlog"） |
| 责任岗位 | 产品负责人主持，全队下注 |
| 工具触点 | 飞书 docx 下注会纪要 + markmap 标记本周押注节点 |
| 产出 | 本周押注清单（1-2 个叶节点），每个有明确闭环判据 |
| 通过判据 | 押注数 ≤2；每个押注能切到几天内闭环；都有闭环判据（Shape Up 下注会 https://basecamp.com/shapeup/2.3-chapter-09 ） |

#### 步骤 S4 · 每日开发（触发：每个工作日）

| 项 | 内容 |
|---|---|
| 触发条件 | 每个工作日 |
| 动作 | 当天叶节点先产一页 spec（pitch）→ 过质量门（一道评审）才算"出" → 围绕节点做一小块（issue 切到几天能完，feature-flag 推内部试用）→ 产物挂回节点 |
| 责任岗位 | 当天认领该叶节点的岗位（多为研发）+ 评审人 |
| 工具触点 | 飞书/obsidian（spec）+ GitHub（issue/PR）+ 挂回 markmap 节点；产物挂载走 external_mirror（出站抄 feishu adapter，入站 webhook 走 `Ezagent.Invocation.dispatch/1`，仿 `apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/inbound_dispatcher.ex:58`） |
| 产出 | 每个工作日 ≥1 个叶节点出 spec 或闭一小步；产物已挂回节点 |
| 通过判据 | spec 过一道评审才算"出"（质量门，别注水）；当天产出已挂回节点（挂载覆盖率不掉）（Linear cycle https://linear.app/method/introduction ；Stripe 质量门 https://www.bringthedonuts.com/essays/building-products-at-stripe/ ） |

#### 步骤 S5 · dogfooding 体验（触发：贯穿每天，每周四集中）

| 项 | 内容 |
|---|---|
| 触发条件 | 全队用这个 workspace 开发 ezagent 真实功能时随时；每周四集中体验 |
| 动作 | 自己用着难受的地方，当场记成一个新痛点节点（不是想象的需求） |
| 责任岗位 | 全队 |
| 工具触点 | workspace 自身（网页出口）+ 飞书 bitable（自用痛点登记），新节点回填进 S2 的树 |
| 产出 | 每周 ≥1 条来自自用的真实痛点进树 |
| 通过判据 | 进树的痛点来自真实使用、不是拍脑袋（Notion 极致 dogfooding https://colossus.com/article/inside-notion/ ；Figma https://openai.com/index/figma-david-kossnick/ ） |

#### 步骤 S6 · 产品+运营跟进（触发：每周五发 changelog；三位一体每天贯穿）

| 项 | 内容 |
|---|---|
| 触发条件 | 每周五发 changelog；"开发节点配套产品+运营节点"每天贯穿（三位一体） |
| 动作 | 把本周做出来的 ezagent 功能写成 changelog（哪怕小也发，经 external_mirror 镜到飞书群让全队对齐）；**对每个推进中的开发节点，检查它配套的产品节点（这功能给哪个用户群体解决什么）和运营节点（怎么让目标用户用上）有没有同步认领、同步推进**——这是"每个开发都有配合的产品和运营跟进"的落地动作 |
| 责任岗位 | 运营 + 产品 |
| 工具触点 | 飞书 docx（changelog）+ 导图（三位一体节点连线）；周报出站走 external_mirror `:push` |
| 产出 | 本周 changelog ≥1 条可感知价值；推进中的开发节点都有配套产品+运营节点在跟（三位一体覆盖率不掉） |
| 通过判据 | changelog 真发了且有价值条目；本周没有"光开发、产品运营缺位"的脱节节点（Linear changelog https://lastrelease.io/blog/how-linear-uses-a-public-changelog ）。**注：对外 PMF 测分（"不能再用会多失望"占比，Superhuman 引擎）属于对外动作，留到内部跑通、出现外部用户后再上，本阶段不做。** |

#### 步骤 S7 · 收口 + 反哺（触发：每周日收指标 / 每 4-6 周结押注）

| 项 | 内容 |
|---|---|
| 触发条件 | 每周日（收指标 + 复盘）；每 4-6 周（结押注 + 重塑树） |
| 动作 | 看闭环看板：北极星（根源价值跟踪率 + 三位一体覆盖率 + 返工下降）+ 输入指标动没动；指标没动→定位卡点→改下周选题。每 4-6 周：押注到点默认不延期（断路器），回看北极星因果假设，验伪方案砍掉、新机会进树、ICE 重排，必要时修北极星 |
| 责任岗位 | 产品负责人（+研发自动汇总） |
| 工具触点 | 闭环看板（数据从节点状态机自动汇总，是网页出口的一个视图）+ 飞书 bitable 趋势 + xmind/markmap 重塑版 |
| 产出 | 周指标快照 + 下周选题已调；每 4-6 周末有有意义成品、北极星已复盘、机会树已回填 |
| 通过判据 | 每个输入指标有数、趋势可见；指标没动当周复盘已改选题；期末树已回填（Lean Build-Measure-Learn https://theleanstartup.com/principles ；Shape Up 断路器 https://basecamp.com/shapeup/2.3-chapter-09 ） |

### 1.2 三层时间盒的"动作清单"速查（贴墙上）

> 三层套：**每天一小块**（内圈）/ **每周一闭环**（中圈）/ **每 4-6 周一押注**（外圈）。下面是可勾选的动作清单。

**每天（雷打不动，对应 S4/S5）**
- [ ] 早 15 分钟：各自 agent 自动汇报"我认领节点昨天进度/今天计划"，人看一眼对齐（落点：socialware 网页出口刷新）
- [ ] 上午：当天叶节点产一页 spec → 过质量门一道评审 → 挂回 markmap 节点
- [ ] 全天：围绕该叶节点做一小块（issue 切到几天能完），feature-flag 推内部试用 → GitHub issue/PR 挂回节点
- [ ] 用着难受当场记成新痛点节点（S5），回填树
- [ ] 晚：产物挂载检查（今天产出都挂回节点了吗，挂载覆盖率别掉）
- 每日验收信号：**当天 ≥1 个叶节点 spec 出了或闭了一小步，且产物已挂回节点。**

**每周（中圈，周一到周日）**

| 周几 | 主题 | 谁主导 | 验收/指标 |
|---|---|---|---|
| 周一 | 下注选题（S3） | 产品负责人 | 本周押注清单定、每个有闭环判据 |
| 周二 | 探索访谈（喂养 S2） | 全队轮值 | ≥1 轮访谈、≥1 条新痛点入树 |
| 周三 | 开发深水区（S4） | 研发 | 押注进度过半 |
| 周四 | dogfooding 集中体验（S5） | 全队 | ≥1 条自用痛点进树 |
| 周五 | 收闭环 + 发 changelog + 三位一体核对（S6） | 运营+产品 | changelog ≥1-2 条可感知闭环；推进中的开发节点都有配套产品+运营节点 |
| 周日 | 指标回收 + 复盘（S7） | 产品 | 北极星（根源跟踪率/三位一体覆盖率/返工）+ 输入指标有数、趋势可见、下周选题已调 |
| —（后置） | 对外 PMF 测分 / 探索访谈轮值 | — | 留到内部跑通、出现外部用户后再上，本阶段不做 |

**每 4-6 周（外圈，对应 S7 收口）**
- [ ] 断路器：押注时间盒到了没做完，默认不延期，回炉重塑（Shape Up 纪律 https://basecamp.com/shapeup/2.3-chapter-09 ）
- [ ] 回看北极星：这几周北极星动没动？输入指标→北极星的因果假设对不对？
- [ ] 重塑机会树：验伪方案砍掉、新机会补进、ICE 重排，必要时修北极星定义——把 S7 的发现回填到 S1/S2，闭环合拢，转下一圈。

## 第二部分 · 有效性评估（五个关键机制逐个体检）

> 每个机制四问：**①解决什么 ②竞品做到什么程度 / 我们凭什么不同 ③可能在哪失效 ④怎么度量它有效**。这是把"听起来很美"压成"能被证伪"。
>
> **参照系纠偏（俞军评审命中，必读）**：本节引用的 Linear / Notion / Figma / Superhuman / Stripe / Basecamp **全是直接竞品，不是给我们背书的前辈**。早先版本把"竞品已规模化交付的能力"叙述成"我们要缝进来的成熟方法"，等于偷换参照系——把要打败的对手写成了背书人。下面每个机制的第②问已改写成**竞品分析**：老实写"这个能力 Linear/Notion 已经做到什么程度，我们凭什么做得不同/更好"，并直面那个要命问题——**用户为什么要从已经做到这些、且体验远好于一个要自己跑 BEAM 的自研工具的产品迁过来**。"方法成熟"≠"缝在一起后用户价值净值为正"（子弹短信每个功能也都成熟，照样打不过微信）。

### 机制 1 · 思维导图驱动（一张图把战略到运营串成逻辑链）

- **解决什么**：痛点 2.1「战略和执行脱节」——定位在 PPT、开发只剩工单、运营另一套 KPI，三段各说各话（`research/D-产品框定.md:84`）。一张机会-方案树强制每个开发节点都能往上追到一个真实痛点，杜绝"为做而做"。
- **竞品做到什么程度 / 我们凭什么不同**：机会-方案树（OST）是公开方法（Teresa Torres https://www.producttalk.org/opportunity-solution-trees/ ），上接 Amazon PR/FAQ（https://workingbackwards.com/concepts/working-backwards-pr-faq-process/ ）、下接 Shape Up pitch（https://basecamp.com/shapeup ）。**但要诚实**：Linear 已有 Roadmap→Projects→Cycles 的成熟树、Notion 已有数据库视图当机会树，这些竞品把"战略树"做得比我们的 markmap 视图体验好得多。**所以"思维导图骨架"在用户感知层面更接近旧要素重新组合，不是真新体验**——用户凭什么从 Linear 的树迁到我们的图？我们能给的差异只有"节点直接绑 agent + 产物自动挂回"，而那一块（agent）恰恰是案例支撑最弱、最不确定的（见机制 3）。**结论：本机制不是差异化来源，是基础设施；别拿它当卖点。**
- **可能在哪失效**：
  1. 树会膨胀成"什么都往上挂"的装饰墙，节点几百个没人看 —— 失去"有的放矢"。
  2. markmap 是渲染库、没在线协作编辑器，多人改图要走会话编辑流或 git PR（`01-工具选型.md:41`），如果团队嫌麻烦就会绕过图、回到群里聊，图变成"画完就死的快照"。
  3. 真相源在 ezagent 库、图只是视图（`01-工具选型.md:17`），如果挂钩牌只在图上不进库，图和真相源会漂移。
- **怎么度量它有效**：① 节点认领率趋近 100%（没人认领=图在装饰，`research/D-产品框定.md:164`）；② 每个叶节点能追到痛点（树连通无孤儿，S2 通过判据）；③ 挂钩牌填齐率——填不齐说明节点悬空。**失效早警**：认领率掉、孤儿节点出现、挂钩牌空着，三个里中一个就说明图在退化成装饰。

### 机制 2 · 节点认领（每个节点显式绑一个责任人，未认领=显式"待分配"）

- **解决什么**：痛点 2.3「对齐成本高」+ 责任无声烂掉。体验承诺 4.2「每个节点都有主」——不存在"既没认领也没标待分配"的灰色节点（`03-思维导图.md:76`）。这条直接呼应 ezagent 的设计哲学"消息没人接收不能静默丢"（`research/D-产品框定.md:103`）。
- **竞品做到什么程度 / 我们凭什么不同**：Figma 的 Maker Week 把"人人可认领、人人挂产物"做成文化（https://openai.com/index/figma-david-kossnick/ ）；Linear 的轮值 goalie 把"客户 bug/需求"显式分流到一个责任人（https://linear.app/method/introduction ）。**诚实**："显式绑责任人"这件事 Linear 的 assignee + triage、Notion 的 person 属性早已规模化交付，且零迁移成本。我们的差异只在"认领=CapBAC Grant、granted_by 不可伪造"这个底层强约束——**但用户感知不到"不可伪造"的价值，他们感知到的是"又要学一套新的认领心智 + 把已有项目从 Linear 搬过来"**。所以这条对"已在用 Linear 的成熟团队"几乎没有迁移拉力；它的真实价值只在"旧体验≈0 的全新团队"上才成立。
- **可能在哪失效**：
  1. 认领变成"占坑"——认了不干，节点长期卡「已认领」却不动，比"待分配"更隐蔽。
  2. 一人认领过多节点，认领率好看但实际是瓶颈。
  3. 认领写在图上没写进库（节点=Kind，认领=绑 User，`04-spec与用户旅程.md:36`），状态机流转和真相源对不上。
- **怎么度量它有效**：① 认领率（已认领/活跃节点）；② 但必须配 **cycle time**（认领→闭环中位耗时，`research/D-产品框定.md:165`）一起看——认领率高 + cycle time 不降 = 占坑信号；③ 长期卡「已认领/进行中」的停滞节点数（负责人介入信号，`04-spec与用户旅程.md:224`）。**单看认领率会骗人，必须和 cycle time 交叉验证。**

### 机制 3 · 个人 agent（每人一个长期 agent 追踪自己的活 + 跨 agent 对话）

- **解决什么**：痛点 2.3「对齐成本高」——把"刷群问做到哪了"变成"问自己的 agent / 让两个 agent 对话"（`research/D-产品框定.md:90`）。这是和 Linear/Notion/飞书最大的差异点：别人是一次性 AI 问答，我们是每人一个长期 agent 当"神经"（`research/D-产品框定.md:35`）。
- **竞品做到什么程度 / 我们凭什么不同**：这一条**没有现成公司做过完全一样的事**——它是 ezagent 的核心卖点、本产品唯一可能的真新体验（`01-工具选型.md:79` 写明"无外部替代，核心卖点，不外包"）。但要把话说全：Linear/Notion/飞书都已有"一次性 AI 问答"，我们的差异是"每人一个**长期** agent 当神经"。机制本身（`Ezagent.Entity.Agent` + flavor，`apps/ezagent_domain_agent/lib/ezagent/entity/agent.ex:86`；agent 平等参会 `docs/discuss/intro/02-领域层全览.md:58`）在 ezagent 里功能上实测过（curl/cc flavor，`docs/discuss/intro/04-如何使用ezagent.md`）——但**"功能能跑"不等于"价值兑现"**。
- **诚实标注 ≠ 已处理风险（俞军评审点破）**：本机制自标"最高不确定性、案例支撑最弱、差异化赌注"——这个诚实是优点，**但它一直被当成免责声明用：标注了不确定，却没改变"把它排进核心路径、不前置验证"的决策**。标注不等于处理。所以本轮已把它的**价值验证前置到技术开发阶段 1**（`05-ezagent技术开发计划.md` 阶段 1 价值闸门）：用最轻 curl flavor、自己 3-5 人、2 周，实测"对齐时长真降了没"——降了再往下，没降就停。**唯一的真新体验恰恰最没把握兑现成正效用，所以它必须最先被证伪，而不是最后才发现。**
- **可能在哪失效**：
  1. **agent 噪音**——每人一个 agent 每天主动汇报/提醒，N 个人 = N 个 agent 刷屏，对齐成本不降反升（这正是第四部分要规避的失败模式）。
  2. agent 答得不准——读"我认领节点"的状态如果和真相源漂移，agent 会自信地说错，比没有 agent 更坏。
  3. 重 agent（cc flavor）要 cc 凭证、可能超时（`.claude/skills/ezagent-socialware/SKILL.md:110-117`），成本和延迟可能撑不起"随时问"。
  4. agent 数随团队人数线性增长的资源管理（MVP 3-10 人无压力，`01-工具选型.md:79`，但放大后是真问题）。
- **怎么度量它有效**：① **对齐时长下降**（每周花在同步会议+刷群的时间，`research/D-产品框定.md:167`）——这是 agent 价值的直接度量，降了才算有效；② agent 回答准确率（抽样核对 agent 说的进度 vs 真相源）；③ agent 主动消息的"有用率"（被人采纳/响应的占比 vs 被忽略的占比）——有用率低就是噪音。**MVP 先用轻量 curl flavor 验证"能追踪 + 能对话"，别一上来全员重 agent**（`04-spec与用户旅程.md:86`）。

### 机制 4 · 网页对齐出口（一个 socialware 公开会话，编排器动态渲染全队状态）

- **解决什么**：痛点 2.3「对齐成本高」+ 2.1「脱节」——把"开会同步 + 刷群问进度"替换成"打开一个网页看一眼"，匿名旁观者也能看（`04-spec与用户旅程.md:104`）。
- **竞品做到什么程度 / 我们凭什么不同**：Linear 用公开 changelog 当对外状态出口（https://lastrelease.io/blog/how-linear-uses-a-public-changelog ）；Notion 整个公司住在 Notion 里当中枢（https://colossus.com/article/inside-notion/ ）。**诚实**："单一对齐面"两家竞品都已交付，且体验成熟稳定。我们的差异是"出口内容由 agent 动态生成、且数据是节点状态机实时汇总"——**但当前这是承诺式的**：编排器现有 9 个工具偏"编排团队"而非"画任意 UI"，复杂可视化可能退回固定模板（见下方失效点 4），而 world/agent-schema 又未进 main。**也就是说我们暂时给不出比 Notion/Linear 更好的对齐面，只能给一个"自己跑 BEAM 才有"的、功能上更弱的版本**——这条对外不构成迁移理由，对内（自己 dogfood）够用。机制落点：`public_view: true` 的 SessionTemplate（`apps/ezagent_domain_session/lib/ezagent/entity/session_template.ex:719`，fail-closed `public_view.ex:38`）。
- **可能在哪失效**（这是落地坑最多的机制，开工前贴墙上，来自 socialware SKILL）：
  1. `public_view?/1` 读**活会话 slice**，会话必须和服务在同一个 BEAM，否则匿名访客被 302 弹去 `/login`（`SKILL.md:126-138`）。
  2. `public_view` 只认字面布尔 `true`，`"true"`/缺失都按私有（`SKILL.md:66-90`）。
  3. 客户 SPA 没 build（`pnpm install` + `mix assets.build`）会 200 白屏（`SKILL.md:143-147`）。
  4. 编排器现有 9 个工具偏"编排团队"而非"画任意 UI"（`tool_catalog.ex`），复杂可视化可能要补工具或退回固定模板视图（`01-工具选型.md:86`）；且 **world / agent-schema 在建未进 main，别当已有能力依赖**（`research/C-方法论与成功案例.md:228`）。
- **怎么度量它有效**：① 匿名访客打开 `/socialware/chat?session_uri=…` 能看到聚合状态（功能 4 闭环判据，`04-spec与用户旅程.md:116`）；② 对齐时长下降（和机制 3 共享这个指标）；③ "看出口替代开会"的实际替代率——还在开同步会就说明出口没真正承载对齐。**兜底**：编排器扛不住就先用固定页面树模板把核心状态（认领率/挂载/本周闭环数）渲染出来，等 world 落地再升级动态 UI（`01-工具选型.md:107`）。

### 机制 5 · dogfooding 节奏（日 spec / 周 1-2 闭环 / 周 1 轮运营调整，自己用自己）

- **解决什么**：痛点 2.4「迭代慢、节奏散」——用强制节奏骨架倒逼速度，自己用自己倒逼真实痛点冒出来（`research/D-产品框定.md:93`）。
- **竞品/方法做到什么程度 / 我们凭什么不同**（这是论证最扎实的机制，但也最该警惕"用成熟方法给自己镀金"）：每天一小块=Linear issue 切到几天能完（https://linear.app/method/introduction ）；每周 changelog 当闭环钟摆=Linear（https://lastrelease.io/blog/how-linear-uses-a-public-changelog ）；每周 PMF 测分=Superhuman 一年把分从 22% 拉到 58%（https://review.firstround.com/how-superhuman-built-an-engine-to-find-product-market-fit/ ）；自己用自己=Notion 泡在 Notion Dev、Figma Maker Week（https://colossus.com/article/inside-notion/ 、https://openai.com/index/figma-david-kossnick/ ）；spec 过质量门=Stripe API Review（https://www.bringthedonuts.com/essays/building-products-at-stripe/ ）；4-6 周押注+断路器=Basecamp Shape Up（https://basecamp.com/shapeup/2.3-chapter-09 ）。**诚实**：这些方法本身成熟，但**它们是"团队纪律"，不是"产品功能"**——任何团队用 Linear+Notion 也能照搬这套节奏，不需要迁到我们的 workspace。所以 dogfooding 节奏是**我们自己该执行的工作方式，不是卖给别人的产品差异点**。它对内（让我们自己迭代更快）价值真实，对外几乎零迁移拉力。
- **可能在哪失效**：
  1. **过度仪式化**——日 spec/周 changelog/周 PMF/周下注会，仪式太多，开会和填表的时间超过干活，节奏从"发动机"变成"枷锁"。
  2. 为凑节奏注水——每天硬憋一个 spec、每周硬发一条假 changelog，指标好看但价值空心（质量门就是防这个，`03-思维导图.md:232`）。
  3. 团队太小（3 人）撑不起这么多角色轮值（goalie/访谈轮值/下注会），节奏空转。
- **怎么度量它有效**：① 北极星本体——**返工下降 + 根源价值跟踪率 + 三位一体覆盖率**（节奏真的在让 ezagent 团队少返工、开发都追得到根、都配齐产品运营，`research/D-产品框定.md:163`）；② 日 spec 产出率趋近 100% **但配挂载覆盖率和质量门通过率一起看**（防注水）；③ cycle time 持续下降（节奏真的在加速迭代）。**关键**：北极星看的是"返工降没降/根源追不追得到/三位一体齐不齐"这种结果，**不是"spec 数 / commit 数 / 周闭环数"这种活动量**——盯结果指标，别盯活动指标。

### 有效性评估小结表

| 机制 | 对外是不是差异点 / 竞品对照 | 最大失效风险 | 唯一最该盯的度量 |
|---|---|---|---|
| 思维导图驱动 | **不是**——Linear 树/Notion 库已做更好，是基础设施非卖点 | 退化成装饰墙 | 认领率 + 挂钩牌填齐率 |
| 节点认领 | **不是**——Linear assignee/triage 零迁移成本已交付 | 认领即占坑 | 认领率 ×cycle time 交叉看 |
| 个人 agent | **唯一可能是**——无同款竞品，但案例最弱、价值未兑现，已前置到阶段 1 验 | agent 噪音 / 答不准 | 对齐时长下降 + agent 有用率 |
| 网页对齐出口 | **暂时不是**——Notion/Linear 对齐面更成熟，我们的还是承诺式 | 落地四坑 + world 未进 main | 匿名能看到聚合状态 + 替代开会率 |
| dogfooding 节奏 | **不是**——是团队纪律非产品功能，任何团队用现成工具也能照搬 | 过度仪式化 / 注水 | 返工下降 + 三位一体覆盖率（结果，非"闭环数"活动量） |

> **一句话**：五个机制里，**四个是"我们自己该用的工作方式 / 基础设施"，对外没有迁移拉力；只有"个人 agent"一个是可能的真差异点，而它恰恰最不确定、价值未验证。** 这就是为什么作为 ezagent 的第一个产品要**先内部跑通**——ROI 和必要性都先收口到"ezagent 团队用它开发自己产品时是否真少返工/少对齐/少废功能"，对外开放留到内部跑通后再议（见第二点五 ROI 实算 + 第三部分必要性）。

### 第二点五 · ROI 实算（不再喊口号，真算一次回本账）

> 俞军评审命中："ROI 闭环"被反复当口号、从没真算过；"有利润"属性整份材料空白。这里把账落到**具体场景**真算一次。定位已钉死：本产品当前是**内部工具**、同时是 **ezagent 的第一个产品**（内部先、外部后）。当前阶段它的 ROI = **让 ezagent 自身的产品开发被根源跟踪 + 三位一体推进，所省下的返工/对齐/脱节成本**——不是抽象的"省时间"，而是 ezagent 团队开发自己产品时实实在在少返工、少开会、少做废功能。

**回本公式（具体场景版）**：

```
投入 = 自研工时（10 周折人天 × 人天成本） + 每月持续维护成本
       + 机会成本（这 10 周 2 个人不直接做 ezagent 主线功能，少推进的那部分主线价值）
回收 = ① 返工下降：开发 ezagent 功能时，因没对齐/没挂钩牌而推倒重做的次数 × 单次返工人天
       + ② 对齐时长降：每周省下的同步会议+刷群分钟 × 参与人数 × 52 周
       + ③ 废功能减少：因开发-产品-运营脱节做出来又没人用的功能 × 单个废功能人天
回本周期 = 投入 ÷ 年化回收
```

**一组示意算法（×号是待实测的回收倍数，结构先立住，数字团队按实情替换）**：

| 项 | 口径 | 示意值 |
|---|---|---|
| 自研投入 | 10 周 × 假设 2 人全职 × 5 天 = 100 人天 | 100 人天 |
| 月维护 | BEAM 节点 + 双向同步 + SPA build 的运维 | 约 3-5 人天/月 |
| **机会成本** | 这 10 周 2 人不直接做的 ezagent 主线功能（少推进的主线价值，按团队实际折算） | 待团队拍板（这是必算项，不能略） |
| 回收① 返工下降 | 阶段 1 实测的返工事件减少数 ×单次返工人天 | 返工下降 **×** 次（待实测） |
| 回收② 对齐时长降 | 阶段 1 实测的每人每周对齐省时 ×人数 ×52 周 | 对齐时长降 **×** 分钟/人/周（待实测） |
| 回收③ 废功能减少 | 因三位一体（开发必配产品+运营节点）而少做的废功能数 ×单个废功能人天 | 废功能减少 **×** 个/季度（待实测） |

**关键诚实点**：
1. **三个回收项的 ×（返工下降数 / 对齐省时 / 废功能减少数）都不能拍脑袋填，全是阶段 1 价值闸门要实测的数**——这把 ROI 直接挂到这个产品要解决的两个根本问题上：价值从根源跟踪（少做废功能）、开发产品运营不脱节（少返工、少对齐）。三个 × 实测都 ≤0，则回本周期 = ∞，**项目本身就不成立**，比任何 ROI 话术都直接。
2. **机会成本是必算项（俞军 C 类必查项）**：这 10 周 2 人全职做 workspace，放弃的是直接做 ezagent 主线功能。"做这个 workspace 的边际收益 > 直接做主线"这句话要能站住——它的合理性有两层：① 这个 workspace **本身就是 ezagent 的第一个产品**（做它=做产品，不是纯内耗）；② 它**同时验证了 ezagent 的 agent/socialware/external_mirror 三套能力**（顺带的技术验证收益，要诚实标明它不是"省时收益"，别和回收①②③混算重复计数）。两层都不成立，这 10 周就该去做主线。
3. **对外商业回报暂时不写、不假装写得出**：作为 ezagent 的第一个产品，对外定价/外部团队迁移是**后续阶段**的事——在"内部 ROI 跑正（三个 × 实测为正）+ 出现第一个外部团队主动要用"之前，本文档不宣称任何对外商业回报，只标"待内部跑通后再议"。

## 第三部分 · 必要性评估（MVP 必须 vs 可后置）

> 判据：**没有它整台发动机转不起来 = MVP 必须；它是放大器/优化项、缺了也能转一圈 = 可后置。** 优先级沿用 `04-spec与用户旅程.md:153` 的 ICE 排序 + 依赖约束。
>
> **先说一句更诚实的话（俞军评审命中）**：必要性不能只按"功能依赖"排，还要按"价值是否已验证"排。**整台发动机真正的成败开关是"个人 agent 能不能降对齐成本"这个未验证赌注**——它在功能依赖图上看似"可后置的放大器"，在价值上却是"赌注不成立则整个差异化归零"的核心。所以它被特殊处理：**功能上后置（先用最轻 curl flavor），但价值验证上前置（阶段 1 硬闸门）**。别被"它是 P 几"的功能优先级骗了，价值优先级和功能优先级是两条线。

### MVP 必须（缺了发动机转不起来）

| 机制/功能 | 为什么必须 | 出处 |
|---|---|---|
| **节点认领（功能 1，P0）** | 整个产品的骨架，别的全挂在它上面；也是最大块自研（ezagent 无现成"图/节点"） | `04-spec与用户旅程.md:45`、`research/A-ezagent能力盘点.md` §5 |
| **产物挂载（功能 2，P0）** | 节点变成唯一索引才解决"找东西翻五个地方"；MVP 至少跑通 GitHub + 飞书两来源（飞书 adapter 现成抄） | `04-spec与用户旅程.md:69`、`apps/ezagent_plugin_feishu/lib/ezagent/plugin_feishu/application.ex:120` |
| **dogfooding 节奏骨架（日 spec/周闭环/周运营）** | 这是发动机本身，缺了就只是一张静态图。**诚实修正**：它是"团队纪律"，对内省时真实、对外无迁移拉力，别把它当产品卖点；且仪式过载有真实失败风险（见第四部分失败模式 1），MVP 第一圈只跑"日 spec + 周 changelog"两个，不是全套 | `03-思维导图.md:216` |
| **一条北极星 + 几个输入指标** | 没有指标就无法做 S7 收口、无法 Build-Measure-Learn，闭环合不拢。**北极星钉在「根源价值跟踪率 + 三位一体覆盖率 + 返工下降」**（直接对应这产品要解决的两个根本问题：价值从根源跟踪、开发产品运营不脱节），不是「周闭环数」（自己数的活动指标，见 S1 诚实提示） | `research/D-产品框定.md:157` |
| **网页对齐出口的最小版（固定模板视图）** | 团队对齐的唯一触点；但 MVP 先用固定页面树模板，不依赖动态编排器。**诚实**：固定模板版在体验上弱于 Notion/Linear，它的价值只在"对内省自己开会时间"，不构成对外迁移理由 | `01-工具选型.md:107`、`04-spec与用户旅程.md:118` |

### 可后置（放大器，缺了也能先转一圈）

| 机制/功能 | 为什么可后置 | 后置到何时上 |
|---|---|---|
| **个人 agent 重 flavor（cc）** | MVP 用轻量 curl flavor 验证"能追踪+能对话"即可，重 agent 按需上；它是差异化赌注但案例支撑最弱，先小成本验证 | curl flavor 验证对齐时长真降、agent 有用率达标后再上 cc（`04-spec与用户旅程.md:86`） |
| **网页出口的动态编排器 UI** | 编排器 9 工具偏编排非画 UI，且 world/agent-schema 在建未进 main——先固定模板，别赌在建能力 | world 落地后升级（`research/C-方法论与成功案例.md:228`） |
| **闭环看板（功能 5，P2）** | 让节奏可见、倒逼速度，但不阻塞别的功能，纯汇总建立在功能 1/4 之上 | 功能 1+4 落地后顺势做（`04-spec与用户旅程.md:140`） |
| **excalidraw/xmind/obsidian connector** | 框架图/个人笔记是锦上添花，MVP 先 GitHub+飞书两条最成熟链路 | GitHub+飞书跑通后按需补（`03-思维导图.md:153`） |
| **对外 PMF 测分 / 探索访谈轮值** | 是对外动作，本阶段单一内部情境用不上；第一圈先跑"日 spec+周 changelog"主循环，PMF 引擎留到内部跑通、开放外部后再上 | 内部跑通、出现外部用户后（`research/C-方法论与成功案例.md:110`） |
| **精细分租户 / 复杂结算** | 先单 workspace，settlement 电商才用 | MVP 明确不做（`04-spec与用户旅程.md:148`） |

**一句话必要性结论**：MVP = 节点认领 + 产物挂载（GitHub/飞书）+ 日spec/周changelog节奏 + 「根源跟踪率 / 三位一体覆盖率 / 返工下降」北极星 + 一个固定模板对齐出口。**个人 agent 用最轻 curl flavor，且在阶段 1 用 2 周实测"开发 ezagent 功能时对齐/返工真降没"当硬闸门——降了发动机才值得继续造，没降就停**；动态 UI 和对外 PMF 引擎后置。**核心收口：先把"ezagent 团队用它开发自己产品时、净值明显为正（少返工、少对齐、少废功能）"做实，作为 ezagent 的第一个产品先内部跑通，再谈对外开放——把不确定性最高（agent 赌注）的那块从"最后才发现"提到"最先证伪"。**

## 第四部分 · 反例 / 风险：常见失败模式及规避

> 这套体系最容易死在三种病上。每种给：**病灶 → 怎么发作 → 怎么规避（带可观测信号）**。

### 失败模式 1 · 过度仪式化（流程压垮产出）

- **病灶**：日 spec + 周 changelog + 周 PMF + 周下注会 + 周访谈 + 周日复盘 + 4-6 周结押注——仪式叠太多，开会填表的时间超过干活。节奏从"发动机"变成"枷锁"。
- **怎么发作**：团队开始为凑节奏注水（硬憋 spec、发假 changelog），指标好看但价值空心；或者干脆静默跳过仪式，SOP 变成墙上贴的死文档。
- **怎么规避**：
  1. **盯结果指标不盯活动指标**——北极星是"返工下降 + 根源跟踪率 + 三位一体覆盖率"，不是"spec 数 / 会议数 / 周闭环数"（`research/D-产品框定.md:163`）。spec 产出率高但返工不降、三位一体覆盖不升 = 仪式空转。
  2. **质量门挡注水**——spec 过一道评审才算"出"，不是写完即出（Stripe 式，`03-思维导图.md:232`）。
  3. **团队太小就砍仪式**——3 人团队第一圈只跑"日 spec + 周 changelog"主循环，PMF/访谈轮值/下注会后置（见第三部分）。
  4. **断路器对仪式也生效**——某个仪式连续几周没产生决策价值，就砍掉它，别因为"流程规定"硬留。
- **可观测信号**：日 spec 产出率 ↑ 但返工不降 / cycle time 不动 / 三位一体覆盖率不升 → 正在仪式化（活动量涨、结果不动）。

### 失败模式 2 · 工具碎片（真相源漂移，回到"翻五个地方"）

- **病灶**：本来要解决"产物散落各工具"，结果工具栈（markmap/excalidraw/GitHub/飞书/obsidian/SQLite）反而更碎，每个工具一份"真相"，对不上。
- **怎么发作**：挂钩牌只画在 markmap 上没进 ezagent 库；GitHub 改了 issue 状态但 webhook 没回写节点；飞书文档改了但没订阅变更——图、外部工具、ezagent 库三方漂移，agent 读到的是过期数据然后自信地说错。
- **怎么规避**：
  1. **真相源唯一且明确**——节点↔认领人↔产物映射只存 ezagent 库（默认 SQLite），外部工具都只是"能被 agent 自动读写的产物容器"，不是真相源（`01-工具选型.md:17`）。判断工具能不能进栈就两条硬标准：产物有稳定 ID/URL/路径能写进库 + agent 能自动读写它（`01-工具选型.md:24`）。
  2. **进出只走两条铁路**——出站 external_mirror（`:push`/`:pull`）、入站统一 `Ezagent.Invocation.dispatch/1`（P14 铁律，不许 PubSub.broadcast 到入站 topic，否则是事故 2.1 根因，`01-工具选型.md:21`、`02-战略到ROI闭环与案例.md:69`）。
  3. **xmind/obsidian 退为兼容/个人场景**，不做团队真相源（本地文件、无云 API、协作弱，`01-工具选型.md:107`）。
  4. **挂载覆盖率当哨兵**——挂了产物的已闭环节点/已闭环节点，趋近 100% 才说明"产物真归位了"（`research/D-产品框定.md:169`）。
- **可观测信号**：挂载覆盖率掉 / agent 回答和真相源对不上 → 工具在碎片化。

### 失败模式 3 · agent 噪音（N 个 agent 把对齐成本搞得更高）

- **病灶**：每人一个 agent 每天主动汇报 + 节点变化就提醒，N 个人 = N 个 agent 刷屏，本来要降对齐成本，结果信息过载、人开始忽略所有 agent 消息。
- **怎么发作**：早 15 分钟 N 个 agent 各汇报一遍没人看；PR 一动就 notify、CI 一挂就 notify，提醒密度高到被静音；agent 间对话产生一堆没结论的 round。
- **怎么规避**：
  1. **agent 主动消息要有"有用率"指标**——被采纳/响应占比 vs 被忽略占比，有用率低就调降提醒密度（机制 3 度量项）。
  2. **聚合而非广播**——早汇报聚合进一个 socialware 网页出口看一眼（`02-战略到ROI闭环与案例.md:85`），而不是 N 条独立推送；用"网页看一眼"替代"N 个 agent 各说一遍"。
  3. **agent 答不准比不答更坏**——先保证 agent 读的是真相源、抽样核对准确率，再放开主动性（机制 3 失效点 2）。
  4. **MVP 先 curl 轻量 flavor**——别一上来全员重 cc agent（成本/延迟/凭证都是负担，`.claude/skills/ezagent-socialware/SKILL.md:110-117`），先验证"能追踪+能对话"且对齐时长真降，再放大。
  5. **跨 agent 对话要有结论回写**——agent 间对话的结论必须回写节点（`04-spec与用户旅程.md:181`），否则是没落地的空聊。
- **可观测信号**：agent 消息量 ↑ 但对齐时长不降、agent 有用率低 → 正在制造噪音。

### 三种失败模式的共同解药

三种病都靠**同一组哨兵指标**早警：**北极星三件（返工下降 + 根源价值跟踪率 + 三位一体覆盖率）+ 对齐时长下降 + 挂载覆盖率 + cycle time + agent 有用率**。注意：**"周闭环数"被降级为活动指标，不再当哨兵的结果项**——它是自己给自己数的，活动量涨而返工不降/三位一体覆盖不升，恰恰是过度仪式化在发作的信号。只要这几个里有一个背离（返工不降 / 根源追不到 / 三位一体覆盖掉 / 对齐时长不降 / 挂载覆盖掉 / cycle time 不缩 / agent 消息没人理），就是某种病在发作，立刻在 S7 周日复盘定位卡点、改下周选题——这正是 Build-Measure-Learn 的 Measure→Learn（https://theleanstartup.com/principles ）。

## 第五部分 · 一句话收口

这套设计用了一批成熟方法（Amazon PR/FAQ、机会-方案树、RICE/ICE、Shape Up、Linear cycle+changelog、Lean Build-Measure-Learn），再用 ezagent 三件套（每人一个 agent、external_mirror 挂产物、socialware 网页出口）托住它转。**但"方法成熟"不等于"产品就成立"，别拿它给产品镀金**：这些方法 Linear/Notion/飞书等竞品大多已交付且体验更好；缝在一起后净值是否为正，要靠实测说话（子弹短信每个功能也成熟，照样打不过微信）。

**本文档的定位收口到一句实话**：这是一个**内部工具，同时是 ezagent 的第一个产品**——先内部 dogfooding（用 ezagent 规范 ezagent 团队自己的产品开发，让价值闭环从根源被跟踪、每个开发都有产品和运营跟进），跑通后适当时间开放外部。当前阶段只服务一个真实情境（ezagent 团队自己开发 ezagent 真实产品），不掺对外动作。**站得住的路径只有一条**：① 阶段 1 用 2 周实测"用它开发 ezagent 功能时对齐/返工真降没"，证伪核心赌注；② 真算一次内部 ROI（返工下降/对齐降/废功能减少三个 × 必须实测、机会成本=这些周不直接做主线必须算）；③ 对内净值跑正、出现第一个外部团队主动要用之前，对外开放/定价只标"待内部跑通后再议"，不宣称商业回报。

度量它有效就盯哨兵——**北极星三件（返工下降 + 根源价值跟踪率 + 三位一体覆盖率）+ 对齐时长下降 + 挂载覆盖率 + cycle time + agent 有用率**——活动量（周闭环数/spec 数）涨而它们不动，就是过度仪式化/工具碎片/agent 噪音三种病之一在发作，回到周日复盘改选题。
